# 🎬 视频转 GIF 动图 (video_to_gif.md)

## 触发条件
- **文件类型**: mp4, mov, avi, webm, mkv 等常见视频格式
- **意图关键词**: 转gif, gif, 做成表情包, 动图

## 这份手册怎么用
下面讲的是**每个旋钮花什么代价、什么素材在意什么**，不是一套照抄的参数。
任务里若给了「素材判定」，那就是本次素材的实际情况，据它自己定参数。
没有判定时，从元数据（分辨率、时长、码率）自行推断。

## 核心事实
GIF 没有帧间压缩，每一帧都近似独立存储。因此体积 ≈ **输出像素数 × 画面复杂度**，
而画面复杂度在真实素材之间可差 **20 倍以上** —— 同样 1440 宽、同样源分辨率，
一段屏幕录制可能只有 1.8 MB，一段全屏渐变却能到 39 MB。

**所以不存在"默认宽度"这种东西。** 任何写死的宽度都会同时坑到两头：
对屏幕录制过度降质，对实拍素材体积失控。

## 各旋钮的代价

**宽度** —— 最大的杠杆，体积约与它的平方成正比，也是清晰度的唯一来源。
- 大片纯色 + 锐利边缘（屏幕录制、界面演示、动画、图表）：复杂度极低，
  宽度给得起。高分屏录屏若压到源宽的四分之一，**文字会直接不可读**。
  这类素材优先保证文字笔画完整。
- 连续渐变、噪点、全屏运动（实拍、游戏、航拍）：复杂度极高，宽度必须收着给。
- 源比目标窄时沿用源宽，**绝不放大**（放大只增体积不增信息）。
- 用户说"小一点 / 发微信 / 当表情包"时，体积优先级高于清晰度，可以大幅降宽。

**帧率** —— 与体积线性相关。12 fps 是通用起点。降帧率会让动作发卡，
而降宽度是平方级杠杆，所以**要减体积优先动宽度**。演示类静态画面可以更低，
需要看清动作时才往上给。

**色数 (`max_colors`)** —— 128 对绝大多数素材足够。提到 256 体积多约两成，
画质提升微不足道。截图/界面这类本来就没几种颜色的素材，128 绰绰有余。

**抖动 (`dither`)** —— 这个最容易搞反，两个方向都实测过：
- 纯色块 + 锐利边缘的素材用 **`none`**。抖动是往平坦区域撒噪点来伪装色阶，
  但屏幕内容本来就没有色阶，撒进去的噪点又破坏了 GIF 的帧间冗余 ——
  **既更胖又更糊**。
- 渐变 / 实拍素材用 **`bayer:bayer_scale=5`**。这类素材关掉抖动会出明显色带。
  `bayer_scale` 取 5 优于 3 与 1（数值越高十字纹越淡）。
- **任何素材都不要用 `sierra2_4a`**：误差扩散每帧噪点都不同，体积翻三倍，
  换来的画质差异可以忽略。

**时长** —— 超过 30 秒整段转必然产出几十 MB。用户未指定范围时默认取前 10 秒，
并在回复中说明已截取。`-ss` 放在 `-i` 之前可快速定位。

## 命令骨架
两步调色板法。两条命令的 `fps` 与 `scale` **必须完全一致**，
否则调色板是按另一组帧统计的，画质明显劣化。

```bash
ffmpeg -v warning -i <输入绝对路径> -vf "fps=12,scale=1440:-1:flags=lanczos,palettegen=max_colors=128" -y <输出目录>/_palette.png
ffmpeg -v warning -i <输入绝对路径> -i <输出目录>/_palette.png -lavfi "fps=12,scale=1440:-1:flags=lanczos [x]; [x][1:v] paletteuse=dither=none" -y <输出目录>/<原名>_converted.gif
rm -f <输出目录>/_palette.png
```

上面这组是**屏幕录制**的取值示例（宽 1440、关抖动）。实拍素材应改成更窄的宽度
配 `dither=bayer:bayer_scale=5`；截取片段则在两条命令上都加 `-ss 0 -t 10`。

不要加 `palettegen=stats_mode=diff`：看似能针对变化区域优化，实测反而增大约 5%。

## 产物偏大时
流水线会把实际体积回喂给你要求重做。此时**把宽度减半**（平方级杠杆，
一步到位），不要去动帧率或色数——那两个降下去画质掉得多、体积省得少。

## 输出规范
- 产物必须写入任务指定的输出目录。
- 输出文件名: `[原文件名]_converted.gif`
- 调色板等临时文件放在输出目录下，并在最后一条命令中删除。
